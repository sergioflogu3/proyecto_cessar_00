# AGENTS.md — SistemaTickets

Aplicación ASP.NET Core 8 MVC de un solo proyecto para gestión de tickets. Sin suite de tests y sin CI. Docker se usa solo como entorno local de desarrollo (ver `CLAUDE.md`).

Lee `docs/constitution.md` y la spec activa (`specs/NNN-*/`) antes de tocar código.

## Inicio rápido

```bash
dotnet restore SistemaTickets.sln
dotnet run --project SistemaTickets/SistemaTickets.csproj
# por defecto https://localhost:7046 (o similar)
```

## Arquitectura

- **Punto de entrada**: `SistemaTickets/Program.cs`
- **Patrón**: MVC + carpetas de dominio/infraestructura en capas dentro del proyecto web
  - `Controllers/` — controladores MVC (no hay controladores de API)
  - `Domain/Entities`, `Domain/Enums`, `Domain/Repositories`, `Domain/Services`
  - `Infrastructure/Persistence` — arranque de NHibernate, mapeos Fluent, implementaciones de repositorios
  - `Infrastructure/Security` — helper de JWT
  - `Infrastructure/Services` — Azure Blob, email, reportes
  - `Models/` — ViewModels organizados por carpeta de funcionalidad
  - `Views/` — vistas Razor con el nombre de cada controlador
  - `ScriptsDB/` — scripts DDL/DML manuales para SQL Server
- **Ruta por defecto**: `{controller=Users}/{action=Login}/{id?}`

## Base de datos (SQL Server + NHibernate)

- ORM: NHibernate 5.x con mapeos FluentNHibernate en `Infrastructure/Persistence/Maps/`
- Dialecto: `MsSql2012Dialect`, driver: `MicrosoftDataSqlClientDriver`
- **Crítico**: `appsettings.json` → `NHibernate:UpdateSchema` controla `SchemaUpdate` al arrancar.
  - `true` = crea/actualiza tablas automáticamente. Pensado **solo para el primer despliegue**.
  - Ponlo en `false` una vez creado el esquema inicial para evitar migraciones accidentales en producción.
- `ConnectionStrings:DefaultConnection` se valida al arrancar (`ValidateConnectionString` en `Program.cs`): la app se niega a iniciar si falta o sigue siendo un placeholder. `appsettings.json` solo contiene placeholders (ver `appsettings.json.example`); el valor real se define con `dotnet user-secrets set "ConnectionStrings:DefaultConnection" "..."` (desarrollo) o la variable de entorno `ConnectionStrings__DefaultConnection` (producción/Docker).
- **Validación del certificado TLS en la conexión SQL (A5)**: las cadenas de conexión de plantilla (`appsettings.json[.example]`, README) usan `Encrypt=True;TrustServerCertificate=False`, lo que exige que el SQL Server presente un certificado en el que el cliente realmente confíe. `Program.cs` registra una advertencia (`Warning`; no es un fallo duro, porque esta opción puede ser legítima, a diferencia de un placeholder) si `TrustServerCertificate=true` aparece en la cadena de conexión fuera de `Development`. El servicio `sqlserver` de `docker-compose.yml` usa su propio certificado autofirmado sin PKI propia, por lo que la cadena de conexión de `app` mantiene `TrustServerCertificate=True` a propósito; hoy solo es seguro porque ese servicio también corre con `ASPNETCORE_ENVIRONMENT=Development` (misma excepción que A3), lo que suprime la advertencia.
- `ScriptsDB/` contiene los scripts DDL canónicos (users, tickets, inventario, campo repuestos). Ejecútalos en orden para crear una base de datos nueva a mano.

## Autenticación

- `Jwt:Key` se valida al arrancar en `Program.cs` (`ValidateJwtKey`): la app se niega a iniciar si la clave falta, tiene menos de 32 caracteres o coincide con un placeholder conocido. Define una clave real con `dotnet user-secrets set "Jwt:Key" "..."` (desarrollo) o la variable de entorno `Jwt__Key` (producción/Docker); nunca un valor literal en `appsettings.json`.
- JWT Bearer + cookie en modo dual:
  1. Respeta la cabecera `Authorization: Bearer <token>` si está presente.
  2. Si no, usa la cookie `jwt` para los flujos MVC del navegador.
- Basado en roles: `Administrador`, `Supervisor`, `Soporte`, `Usuario`.
- Las peticiones HTML no autenticadas a páginas protegidas se **redirigen a `/Users/Login`** (no devuelven un 401 JSON). **El orden importa aquí**: `app.UseStatusCodePages(...)` en `Program.cs` debe registrarse *antes* de `UseAuthentication()`/`UseAuthorization()`. Cada llamada `Use...` envuelve el resto del pipeline; cuando `UseAuthorization` rechaza una petición cortocircuita (Challenge/Forbid) sin llamar a lo que viene después, así que si `UseStatusCodePages` estuviera después de `UseAuthorization` (como estaba originalmente) nunca se ejecutaría para un 401/403 y el navegador recibiría una página en blanco en lugar de una redirección ante una sesión expirada o inválida. No lo vuelvas a mover hacia abajo al tocar esta parte del pipeline.
- `[ValidateAntiForgeryToken]` se usa en los POST.
- **Sin enumeración de usuarios en el login (M1)**: `UsersController.Login` muestra un único mensaje genérico (`LoginGenericoError`) tanto si el login no existe, como si la contraseña es incorrecta o el usuario está inactivo. `UsuarioService.ValidateCredentialsAsync` también iguala el *tiempo*: cuando no hay un usuario activo que coincida, ejecuta igualmente `EncryptionHelper.VerifyPassword` contra un hash BCrypt ficticio (`DummyPasswordHash`, generado una vez al cargar la clase a partir de un GUID aleatorio) en lugar de retornar antes, de modo que la latencia de la respuesta tampoco sirva para descubrir nombres de usuario válidos.
- **Política de contraseñas (M2)**: `Infrastructure/Security/PasswordPolicy` tiene `MinLength = 12`, `EsContraseñaComun` (comprobación contra lista de bloqueo) y `TieneComplejidadSuficiente` (exige minúscula + mayúscula + dígito + un carácter no alfanumérico). Dos `ValidationAttribute` en `Models/Validation/` las envuelven, `[NotCommonPassword]` y `[PasswordComplexity]`, y se aplican juntos a `UsuarioFormViewModel.Password` y `CambiarPasswordViewModel.NuevoPassword`, junto con un `MinimumLength`/`MinLength` subido a 12. La lista de contraseñas comunes es `10k-most-common.txt` de SecLists (licencia MIT), incrustada en el ensamblado como el recurso `SistemaTickets.CommonPasswords.txt` (ver la entrada `EmbeddedResource`/`LogicalName` en `SistemaTickets.csproj`; no basta con dejar un archivo nuevo en esa carpeta esperando que se recoja solo). `UsersController.CambiarPassword` muestra el mensaje de error real de `ModelState` en lugar de un genérico "Datos inválidos." para que la política sea visible al incumplirla, y los tres campos de contraseña de `Views/Users/Create.cshtml`, `Views/Users/Index.cshtml` (modal de edición) y `Views/Shared/_Layout.cshtml` (modal de cambio de contraseña) muestran de antemano un texto `form-text`; el modal de `_Layout.cshtml` además hace una pre-comprobación con regex en el cliente de las mismas cuatro reglas de complejidad (la comprobación del lado servidor sigue siendo la autoridad).
- **Logout por POST (M5)**: `UsersController.Logout` pasó de `[HttpGet]` a `[HttpPost] [ValidateAntiForgeryToken]`. Un GET se define como método HTTP "seguro" y no necesita interacción del usuario para dispararse: cualquier página de terceros podía terminar la sesión de un usuario con algo tan simple como `<img src="/Users/Logout">`, sin clic. El enlace "Salir" de la barra lateral en `Views/Shared/_Layout.cshtml` pasó de `<a>` a un `<form method="post">` (con `@Html.AntiForgeryToken()`) que envuelve un `<button type="submit" class="sidebar-logout">`; `wwwroot/css/site.css` recibió el reseteo de estilos del navegador correspondiente `button.sidebar-logout` (mismo patrón ya usado para `button.sidebar-link`, el disparador de "Cambiar contraseña").
- **Guardia de identidad válida (M4)**: `Infrastructure/Security/RequireValidUserIdFilter` (un `IActionFilter` global, registrado con `AddControllersWithViews(options => options.Filters.Add<RequireValidUserIdFilter>())` en `Program.cs`) se ejecuta antes de cada acción de controlador de la app, omite las acciones con `[AllowAnonymous]` (así `Login`/`Logout` no se ven afectados) y cortocircuita con `401 Unauthorized` si `ClaimTypes.NameIdentifier` falta o no es un `int` válido. Reemplaza el antiguo patrón por controlador `int.Parse(User.FindFirst(ClaimTypes.NameIdentifier)?.Value ?? "0")` (`UsersController`, `TicketsController`, `InventarioController`, `CampoController`, `DashboardController`), que antes caía en silencio a `UsuarioId=0` en lugar de rechazar la petición; esos puntos son ahora un simple `int.Parse(User.FindFirst(ClaimTypes.NameIdentifier)!.Value)`, y el `!` es seguro precisamente porque el filtro ya validó el claim antes en el mismo pipeline de la petición. Si añades un controlador/acción nuevo que lea este claim, no hace falta volver a comprobarlo: el filtro ya cubre todas las rutas salvo las explícitamente anónimas.
- **Auditoría de cambios de rol/desactivación (M3)**: `UsersController.Edit`/`Deactivate` pasan el id del administrador que actúa (`ClaimTypes.NameIdentifier`) a `UsuarioService.UpdateAsync`/`DeactivateAsync`, que escriben una fila en `AuditoriaUsuarios` (con `IUsuarioRepository.RegistrarAuditoriaAsync`, tabla nueva en `ScriptsDB/auditoria_usuarios.sql`) cuando `Rol` o `Activo` cambian de verdad. Las columnas son `UsuarioId` (usuario afectado), `ModificadoPorId` (administrador que actúa), `Campo` (`"Rol"`/`"Activo"`), `ValorAnterior`, `ValorNuevo`, `FechaCambio`. **Problema de NHibernate que apareció al construirlo**: `existing` (de `GetByIdAsync`) y la instancia que `MergeAsync` modifica son el *mismo objeto* (misma `ISession`, misma entrada del identity map para ese Id), así que comparar `existing.Rol != updated.Rol` *después* de llamar a `_usuarioRepository.UpdateAsync(...)` siempre da falso (el merge ya sobrescribió `existing.Rol` en el sitio). El valor anterior hay que capturarlo en una variable local (`rolAnterior`/`estabaActivo`) *antes* de la llamada de actualización. Si añades más campos auditados, sigue el mismo orden de captura antes de actualizar.
- **Vigencia y revocación de tokens (C3)**: `Jwt:ExpireMinutes` (por defecto 30) está conectado de verdad a `JwtHelper.CreateToken` y al `Expires` de la cookie `jwt`. Cada token lleva un claim `jti`. El evento `OnTokenValidated` de `Program.cs` rechaza una petición si el `jti` está en `ITokenRevocationService` (en memoria, `Infrastructure/Services/InMemoryTokenRevocationService`) o si el usuario buscado por `ClaimTypes.NameIdentifier` no existe o tiene `Activo == false`; así, un usuario desactivado o un token robado pero ya cerrado se rechaza en la **siguiente petición**, no solo al expirar el token. `UsersController.Logout` revoca el `jti` del token actual antes de borrar la cookie. Limitación conocida: la lista de revocación es solo en memoria (se reinicia con la app y no se comparte entre instancias); migra a una tabla persistente `RevokedTokens` si despliegas con varias instancias o con reinicios frecuentes.
- **Sesiones solo HTTPS (A3)**: la cookie `jwt` (`UsersController.Login`) se establece con `Secure = !_environment.IsDevelopment()`: siempre `true` fuera de `Development`, nunca depende del esquema de la petición actual, para que un proxy mal configurado no pueda degradarla en silencio. En `Development` el flag es `false` a propósito, para que `dotnet run --launch-profile http` siga funcionando en local sin certificado de confianza. `RequireHttpsMetadata` de `AddJwtBearer` es `true` (esta app no usa `Authority`/descubrimiento de metadatos, así que hoy no hace nada, pero elimina un flag permisivo que no tenía motivo para ser `false`). `AddHsts` se configura con `Preload = true`, `IncludeSubDomains = true`, `MaxAge = 365 días` (sigue aplicándose solo fuera de `Development`, con la llamada existente a `app.UseHsts()`). `Properties/launchSettings.json` lista primero el perfil `https` (así es el predeterminado de `dotnet run`); HTTPS sigue siendo la forma recomendada de probar en local, y HTTP es una comodidad deliberada solo de Development.
  - El servicio `app` de `docker-compose.yml` corre ahora con `ASPNETCORE_ENVIRONMENT=Development` (cambiado desde `Production`) y se publica directo al host en `${APP_HOST:-127.0.0.1}:${APP_PORT:-8080}` (ambos sobrescribibles en `.env`); esa combinación es lo que permite que `http://localhost:8080` mantenga un login. Vuelve a ponerlo en `Production` para simular un despliegue real; entonces el puerto HTTP directo deja de mantener el login y el servicio `caddy` (TLS autofirmado, `https://localhost:8443`, host/puerto sin parametrizar) es la única entrada.
- **Protección contra fuerza bruta en el login (A1)**: `UsersController.Login` (POST) lleva `[EnableRateLimiting("login")]`, respaldado por una política de ventana deslizante en `Program.cs` (`AddRateLimiter`) que limita las peticiones por IP de cliente (10/min) y devuelve 429 al excederlas. De forma independiente, `ILoginAttemptService` (en memoria, `Infrastructure/Services/InMemoryLoginAttemptService`) bloquea un identificador de login dado (usuario/email/teléfono, sin distinguir mayúsculas) durante 15 minutos tras 5 intentos fallidos en una ventana de 15 minutos; se comprueba antes de ejecutar `ValidateCredentialsAsync`. Cada intento fallido y cada bloqueo se registra con `ILogger<UsersController>` (IP + identificador de login, nunca la contraseña). Limitaciones conocidas: ambos mecanismos son en memoria y por instancia (misma salvedad que la lista de revocación de tokens), y el bloqueo por usuario es en sí un compromiso de disponibilidad: un atacante que conozca un nombre de usuario puede provocar bloqueos repetidos desde IP rotativas; se acepta aquí porque la alternativa (sin bloqueo) es peor, pero conviene revisarlo (p. ej. con CAPTCHA) si se vuelve una molestia real.

- **Validación de adjuntos de tickets (A2)**: `TicketsController.Create` comprueba el tamaño, la lista de extensiones permitidas y la firma del contenido del archivo ("magic bytes") con `Infrastructure/Security/AttachmentValidator` antes de subirlo; ver `AttachmentValidator.AllowedTypes` para la lista vigente (pdf, jpg/jpeg, png, gif, webp, doc, docx, xls, xlsx, txt, csv). El `IFormFile.ContentType` que envía el cliente nunca se acepta ni se guarda; se usa el tipo MIME canónico que devuelve el validador. `TicketsController.DescargarAdjunto` sirve siempre los adjuntos como descarga forzada (`Content-Disposition: attachment`, con la sobrecarga `File(..., fileDownloadName)`) más una cabecera explícita `X-Content-Type-Options: nosniff`, de modo que el navegador nunca renderiza en línea un archivo almacenado, sea cual sea su content-type.
- **Sin detalles internos de excepciones al cliente (A4)**: `UsersController`, `TicketsController`, `InventarioController` y `CampoController` tienen cada uno un helper privado `JsonError(Exception ex, string accion)` (respaldado por `ILogger<TController>`) usado en todos los bloques `catch (Exception ex)` de acciones AJAX. `InvalidOperationException` es el único tipo que la capa de servicios lanza deliberadamente con un mensaje seguro para el usuario (p. ej. "Ticket no encontrado"); ese mensaje pasa tal cual. Todo lo demás (errores de NHibernate/SqlClient, etc.) se registra completo en el servidor y el cliente solo recibe un mensaje genérico "Ocurrió un error inesperado". Si añades una acción AJAX nueva con su propio `catch`, usa el `JsonError` del controlador (o la misma división InvalidOperationException-vs-el-resto) en lugar de devolver `ex.Message` directamente.

## Dependencias externas

- **Azure Blob Storage** (`AzureBlobStorageService`) para los adjuntos de tickets. Configuración: `AzureBlobStorage:ConnectionString` / `ContainerName`. **Secretos fuera del repo desde el primer día (M6)**: `AzureBlobStorage:ConnectionString` se valida al arrancar (`ValidateAzureBlobStorageConnectionString` en `Program.cs`, lanza una excepción si está vacío; no hay comprobación de texto placeholder como en `Jwt:Key`/la cadena de conexión de la BD, porque el valor por defecto versionado `UseDevelopmentStorage=true` es un valor genuinamente funcional para el emulador local Azurite, no algo que reemplazar en desarrollo). La cadena de conexión de una cuenta real de Azure Storage va en `AzureBlobStorage__ConnectionString` (variable de entorno; `docker-compose.yml` la lee del `.env` ignorado por git, ver `AZURE_BLOB_CONNECTION_STRING` en `.env.example`) o en un gestor de secretos; nunca fija en `appsettings.json` ni en `docker-compose.yml`.
- **Email** por SMTP (valores de Gmail en la configuración). Configuración: `Email:*`. Realmente opcional: a diferencia de la cadena de conexión de blob storage, `EmailService` simplemente omite el envío (`LogDebug`, sin error) si `Email:SmtpHost` está vacío, así que no hay validación al arrancar (M6). Si configuras credenciales SMTP reales, van por `dotnet user-secrets` (desarrollo) o las variables de entorno `Email__Username`/`Email__Password`/`Email__FromAddress`/etc.; el servicio `app` de `docker-compose.yml` las toma de `EMAIL_USERNAME`/`EMAIL_PASSWORD`/`EMAIL_FROM_ADDRESS` en el `.env` ignorado por git (vacías por defecto, mismo comportamiento de no enviar correo que hoy); nunca fijas en `appsettings.json`.
- **Reportes**: QuestPDF + ClosedXML.

## Notas de compilación / ejecución

- No existen proyectos de test. La verificación es manual o ejecutando la app.
- `libman.json` está presente pero vacío; las librerías cliente probablemente están incluidas en `wwwroot/`.
- Flujo estándar de `dotnet build` / `dotnet run`.
- **Higiene de dependencias (B2)**: los `PackageReference` directos de `SistemaTickets.csproj` se subieron a su último minor/patch (NHibernate 5.7.0, FluentNHibernate 3.5.0, Microsoft.Data.SqlClient 7.1.0, Microsoft.AspNetCore.Authentication.JwtBearer 8.0.31, fijado dentro de la línea 8.x a propósito, sin saltar al paquete 10.x no relacionado que también existe en NuGet; QuestPDF 2024.12.3, ClosedXML 0.105.1, Azure.Storage.Blobs 12.29.2, BCrypt.Net-Next 4.2.0), más dos fijaciones transitivas explícitas (`System.Net.Http` 4.3.4, `System.Security.Cryptography.X509Certificates` 4.3.2; ambas llegan por `Antlr3.Runtime` de NHibernate → el antiguo `NETStandard.Library`, ver `cambios/B2-dependencias-vulnerables.md` para el grafo de dependencias). `dotnet list SistemaTickets.sln package --vulnerable --include-transitive` reporta cero vulnerabilidades conocidas a la fecha de escribir esto; vuelve a ejecutarlo periódicamente, no está automatizado (aún no hay CI/Dependabot instalado, ver abajo).

- **Saneamiento de logs (B4)**: dos correcciones.
  - **Eco de SQL de NHibernate** (el hallazgo real): `NHibernateBootstrap.BuildSessionFactory` llamaba a `.ShowSql()` incondicionalmente. NHibernate escribe cada sentencia SQL con los valores de los parámetros directamente en `Console`, saltándose por completo `Microsoft.Extensions.Logging` (ningún `LogLevel`, ni siquiera el override de `Microsoft: Warning` de abajo, lo tocaba nunca). Eso eran títulos/descripciones de tickets, nombres de usuario, etc. en la salida estándar en cada consulta y en cualquier entorno. Ahora está condicionado a un parámetro `showSql`, que `Program.cs` pasa como `builder.Environment.IsDevelopment()`. Verificado en Docker: el mismo intento de login produjo 1 línea `NHibernate: ...` en la consola en `Development` y 0 en `Production`.
  - **Namespace `Microsoft` en `Warning` en producción**: `appsettings.Production.json` (nuevo) fija `Logging:LogLevel:Microsoft` en `Warning`, más amplio que el `Microsoft.AspNetCore: Warning` del archivo base (que solo cubre ese subnamespace y sigue aplicando tal cual en Development, sin cambios, ya era el valor ahí antes de B4). Solo tiene efecto con `ASPNETCORE_ENVIRONMENT=Production`; verificado que las líneas de arranque `info: Microsoft.Hosting.Lifetime[...]` y otros logs de nivel Information de `Microsoft.*` desaparecen ahí, y solo quedan `warn:` o superior.
  - Se revisó cada llamada `_logger.Log*` del código: nada registra el JWT en bruto ni un volcado de claims; el único hallazgo de datos personales (`EmailService.SendTicketCopyAsync` registrando en `Information` el email descifrado del destinatario) se corrigió para registrar `solicitante.Id`.
- **`AllowedHosts` (B3)**: `"localhost;127.0.0.1"`, no `"*"`. El middleware de filtrado de hosts rechaza (400) cualquier petición cuya cabecera `Host` no coincida, mitigando la inyección de la cabecera Host. Estos son los únicos hosts que realmente sirven la app en cualquier entorno documentado (`dotnet run`, Docker directo en `localhost:8080`, Caddy en `https://localhost:8443`; Caddy reenvía el `Host` original, que sigue siendo `localhost`). No hay un dominio de producción real documentado en este repo; desplegar detrás de uno implica actualizar `AllowedHosts` (separado por punto y coma) o todas las peticiones darán 400. Poner `APP_HOST=0.0.0.0` en `.env` para acceso por LAN tiene el mismo requisito: la IP/nombre de la LAN debe añadirse aquí también.

## Seguridad

- No subas secretos reales en `appsettings.json`. Hay valores placeholder para `Jwt:Key`, `Encryption:Key` y `ConnectionStrings:DefaultConnection`; `Jwt:Key` y `ConnectionStrings:DefaultConnection` se exigen al arrancar (`Program.cs`) y `appsettings.json.example` documenta la forma esperada.
